# Working on Vanda

Vanda is a screen-centric admin framework for Laravel, a rethought Orchid. Screens are PHP
classes; the server sends a typed page description (IR, `vanda/v1`) and a prebuilt React
renderer draws it. Read `vanda-analysis.md` for the why; this file is the how.

This file is about developing Vanda itself. How to write screens with it (what an app's developer
and their agent need) ships with the package in `packages/core/resources/boost/`: the short rules in
`guidelines/core.blade.php` (Laravel Boost loads them into every prompt) and the full guide in
`skills/vanda-screens/SKILL.md` (loaded when a task touches screens). A change to how screens are
written (a new field or option, a renamed method, a new convention) updates them in the same change,
and every example there must work as written.

## Layout

| Path | What |
|---|---|
| `packages/core` | PHP package `vanda/core`: Screen, nodes, IR, state snapshot, actions, reactions, validation, CLI, test helper |
| `packages/renderer` | TypeScript package `@vanda/renderer`: React 19 + React Aria + Tailwind 4. Builds into `packages/core/resources/dist` |
| `packages/schema/fixtures` | Data shared by PHP and TS tests (expression semantics) |
| `apps/playground` | Laravel 13 app wired to `packages/core` through a path repository (users, roles, pages tree, dashboard, showcase) |

## Commands

```bash
# PHP core
cd packages/core && composer install && vendor/bin/pest

# Renderer (from the repo root)
npm install
npm run typecheck && npm test
npm run build          # REQUIRED after any renderer change: PHP serves the built files

# Playground
cd apps/playground && php artisan migrate:fresh --seed && php artisan serve
php artisan vanda:screens
php artisan vanda:inspect /admin/users/1/edit        # add --json for the raw IR
php artisan vanda:check                              # build every screen; --json for agents, exit 1 on problems
```

## Rules

- **No magic.** No `__call`, no string references to methods. Every option is a typed method; variants are enums (`Variant`, `Tone`, `InputType`).
- **Actions** are screen methods with `#[Action]`; buttons point to them with first-class callables: `->action($this->save(...))`. Never expose a method any other way.
- **State** lives in public typed screen properties. It travels as signed JSON (`Snapshot`), never PHP `serialize`. Models and `#[Locked]` properties are never writable from the browser.
- **Browser input is whitelisted**: only paths of editable fields present on the screen are applied (`ScreenRuntime::applyClientState`), after `Field::sanitize()` for structured values.
- **Access**: `#[Can]` on a screen class or an action method; buttons, modal toggles and menu items that lead to forbidden things are hidden automatically, and the server checks again on every request.
- **Secrets** (`#[Secret]` on a Form property) are accepted from the browser but never written to page state or the snapshot.
- **Validation scope**: a button inside `Layout::modal()` validates only that modal's fields; a button in the `->commands()` of `Layout::section()` or `Layout::card()` validates only that block (the `ValidationScope` interface); any other button validates everything outside modals.
- **One border per level**: a card has a border, the fields in it have theirs, nothing in between gets a box. Groups inside a card are divided by a line or spacing. The Repeater follows it: one field → a list of inputs, up to four short fields → a table with the labels once, anything else → blocks divided by a line (`RepeaterLayout`, chosen in `Repeater::resolvedLayout()`, overridable with `->layout()`); rows are reordered by their grip (mouse, finger, arrow keys); a label equal to the section's title is not repeated.
- **Blocks**: `Layout::section()` puts the title and description above a card with the fields, its buttons at the bottom of the card (forms); `Layout::card()` puts the title inside the card with its buttons beside it (lists, tables, tabs). A button that works on one block goes in that block's `->commands()`, not in the screen's command bar. Blocks inside the content frame are flat (a border, no shadow): only the frame floats. A top-level modal takes no place on the page.
- **Widths**: a page made only of sections (and alerts, tabs of sections) keeps to 1120px, its header too (`isFormLayout()` in `formLayout.ts`); a page with a table, card, chart or metrics takes the full width. `Layout::grid()` counts columns by the width of its block (container queries, `@xl:`), never the window's. The command bar beside the title folds its secondary buttons into «⋯» when they no longer fit in one line (primary buttons and buttons with a hotkey stay) and unfolds them when there is room. Breadcrumbs lead up to the page (its own crumb would repeat the title under it, so it is left out) and stay on one line: more than three become the first, «…» (a menu of the rest) and the last two; a long name ends with «…».
- **Navigation** goes through Inertia (`router.visit`, `<Link>`); reactions and actions stay on Vanda's JSON protocol in `transport.ts`.
- **Saving stays on the screen**: a save action returns `Result::toast('Saved')`; a record created on a create screen opens at its edit URL with `Result::toast('Created')->redirect(self::class, ['item' => $this->item])`. Only deleting goes back to the list. A toast before a redirect is shown on the next page.
- **Values the browser decides** (where a tree row was dropped) reach an action only through `ActionCall::withInput($this->move(...), ['id', 'parent', 'position'])`: the token signs the argument names, the server keeps only those names and scalar values. Never sign a token for arbitrary client arguments.
- **Uploads** are multipart POSTs to the screen's own URL (`type=upload`, `field=<path>`, also `form.rows.2.image` inside a Repeater), so the screen's `#[Can]` and middleware apply. `Upload::store()` checks size and type (no `.php`, no SVG under `image/*`); `Upload::sanitize()` keeps only values already in the field or uploaded by the current user. The value is the attachment id or, with `->target(UploadTarget::RelativeUrl)`, the file's URL. `->crop(Crop::size(556, 322), ...)` crops in the browser (cropperjs) before the upload; the server never crops.
- **Options from the server**: a `Relation` field asks for its records with a JSON request `type=options` (`ScreenRuntime::options()`), after the browser's values are applied, so its query may read other fields.
- **Values a field accepts by itself** come from `Field::implicitRules()`: a Select only its options (unless `->allowCustom()`), a Relation only records of its query. They run with every validating action, next to `->rules()`.
- **Blade islands**: `Layout::view('name', fn () => [...])` renders a Blade view on the server into a `view` node, again on every update. It is static HTML (scripts do not run); anything interactive is a node type.
- **Rich text** is Tiptap (MIT, every `@tiptap/*` package on one version) in the lazy `richtext` chunk; its extensions live in `richtext-extensions.ts`. The server cleans it with `Vanda\Support\Html::clean()`: tags and attributes from `Html::TAGS`, CSS from `Html::STYLES` (each property with a value pattern; never `url()`), `<iframe>` only from `RichText::embeds()` hosts. The editor must produce only that markup: a new feature that writes a new tag, attribute or style adds it to `Html` (and a test) in the same change. `RichText` sends `elements`/`styles` in the IR; text that has other markup opens in HTML mode, and text the user did not change is saved as it was (the editor's own rewrite on load, including its trailing empty paragraph, is not an edit). Images go into the text only with `RichText::uploads()`, through the screen's upload URL. Pasted Word/Google Docs HTML is reduced by `cleanPastedHtml()`. The Markdown preview escapes raw HTML and drops unsafe links.
- **Phones** (below Tailwind's `md`, `MOBILE_QUERY` in `ui.tsx`): a tab bar at the bottom with three menu items (`MenuItem::pinned()`, else the user's favourites topped up with the first items), search and «Меню» (the whole menu in a bottom sheet); the command bar keeps its primary buttons and folds the rest into «⋯»; table rows become cards without the columns marked `TD::hideOnMobile()`, sorting is a «Сортировка» picker; modals become bottom sheets; fields type at 16px (Safari zooms into smaller ones; a rule in `styles.css`). A component that needs another structure on phones uses `useMediaQuery(MOBILE_QUERY)` (never render both and hide one: hotkeys would register twice); spacing uses `md:` classes. Nothing may widen the page: scrollers that hold wide content are `relative overflow-x-auto`; a row that scrolls sideways (tabs, a toolbar) takes `useOverflowFade()` with `vanda-fade-x`, so its hidden end fades and its selected item is in view.
- **Scrolling** (from `md` up): the page itself never scrolls. The menu and the content card scroll each on their own, the card's header (breadcrumbs, bell) stays. The content is Inertia's `scroll-region` (back to the top on a new page, restored on «Back», kept with `preserveScroll`); the menu keeps its place between pages and brings the current item into view on a page opened by its address. Phones scroll the page as before.
- **Heavy renderer components** (dates, tree, editors, charts, map, cropper) load as separate chunks through `chunk()` in `NodeView.tsx`. Keep new heavy dependencies out of the main bundle the same way, and give the type a case in `Placeholder` (same file) with its label and final height, so the page does not jump when the chunk arrives.
- **Menu**: a titled group folds away (remembered in the browser, the current page's group stays open); a star puts an item into «Избранное» at the top (`menuPrefs.ts`, per browser). The button left of the breadcrumbs folds the menu into a rail of icons (`MenuRail`; labels beside the icons on hover or focus, a badge becomes a dot, the user's avatar opens their card with the theme and density); the choice is remembered in the browser, without one the menu is a rail below 1280px. Below 1024px it is always the rail and the button opens the whole menu over the content (a link in it closes it).
- **Density**: `config('vanda.density')` (`Vanda\Navigation\Density`: comfortable or compact) is the panel's; each user may pick the other one beside the theme switch (per browser; picking the panel's own forgets the choice). It puts `data-density` on `<html>` (the server before the first paint, `main.tsx` with the user's choice) and changes only the tokens in `styles.css`: `--v-control` (fields and buttons), `--v-cell-y` (table rows), `--v-block` (card padding), `--v-stack` (space between fields), `--v-menu-item`, with `compact:` classes for the rest. Phones keep the comfortable sizes. A new component takes its heights and paddings from these tokens (`h-(--v-control)`, never `h-9` for something a user types into or presses).
- **Tables**: «+ Фильтр» asks for one filter at a time (field, then value); a filter in use is a chip that opens the same editor, × removes it. A table wider than its block keeps its first column (and the checkboxes) on the left and the row menu on the right, with opaque cells and a shadow where columns scroll under them. The first column never takes more than 40% of the table (`max(15rem, 40cqw)`, the scroller is a size container); `TD::truncate()` ends any other long text with «…», and the whole text shows on hover only when it is cut.
- **Search** ignores case in every alphabet («анна» finds «Анна»): the table's search, text filters and `Relation` go through `Vanda\Support\Search` (`ILIKE` on PostgreSQL, a Unicode `vanda_fold()` on SQLite, `%` and `_` matched as themselves). Write `Panel::search()` providers with `Search::apply()` too, never `where($column, 'like', ...)` on text a user typed.
- **Keyboard and screen readers**: «К содержимому» is the first stop of Tab; a new page (another path, not a sort or a filter) moves the focus to its `h1`. A row with a link has its name as a real link (`RowLinkCell` in `nodes/rows.tsx`: Cmd/Ctrl, Shift and the middle button open a new tab; `rowClickHandlers` for the rest of the row), and its checkbox and «⋯» carry its name («Выбрать: Анна Смирнова», `DropDownView` `name`). Composite widgets are one stop of Tab with arrows inside: tabs are React Aria's `Tabs` (panels stay mounted and inert), the tree moves by arrows, Home/End and Alt+arrows, its rows draw a 2px ring inside. In the menu only the current page's star is a stop of Tab. The edge of a field, a checkbox or a radio is `border-control-line` (3:1, WCAG 1.4.11), never `border-line-strong`. In Tailwind 4 a ring on an element with `outline-none` needs `outline-solid` next to `outline-2`. An icon-only button has an `aria-label`; never put `aria-label` on a plain `span`.
- **Dangerous actions**: undo beats asking. «Отменить» in the unsaved changes bar and removing a filled Repeater or KeyValue row act at once and offer «Вернуть» in a toast (`store.notify()` with an `action`: it stays until used or closed and leaves with its page). What cannot be undone asks with `->confirm($text, $title, $button)`: the title names the action and the record («Удалить роль «Менеджер»?»), the text says what is lost and whom it touches (with counts), the button is a verb and an object («Удалить роль»), `:count` in a bulk action is the number of rows chosen. A dangerous dialog opens on «Отмена». Leaving a page with unsaved changes asks in the panel's dialog («Остаться» / «Уйти без сохранения»), never `window.confirm`.
- **Back links**: an edit screen has no «Назад» button in its command bar; the breadcrumbs (or the phone's back link) lead to the list.
- **Read-only fields** (`->readonly()`) look like values, not inputs: no border, a soft fill, no chevrons; selects, dates and relations do not open.
- **A record's screen** returns `avatar()` and `badge()` for its header; the renderer then draws the design's record header. The "unsaved changes" bar and the leave warning come for free on any screen whose command bar has a primary button with an action. Toasts rise above that bar while it is shown.
- **Impersonation** goes only through `Vanda\Access\Impersonation::loginAs()` inside an `#[Action]` guarded by `#[Can]`; the panel shows the banner and the way back by itself.
- **Weak passwords**: `Vanda\Auth\WeakPassword` checks the password at sign-in (the only moment it is known) and binds the result to the password's hash in the session; on production (or `vanda.weak_password_banner` = true) every page gets a red strip from `app.alerts` with a link to `Panel::profile()`. Changing the password removes it.
- **Branding**: the orchid mark and the logo are vector paths in `packages/renderer/src/logo.tsx` (from `packages/core/resources/images/`); the orchid takes the brand colour (`vanda.brand`, green by default), the letters the text colour; the brand is set on `<html>` (`--v-accent`, and `--v-on-accent` from `onAccent()` in `color.ts`: white, or dark ink on a light brand), so dialogs, menus and calendars in `<body>` follow it, and text or marks on the brand are `text-on-accent`, never `text-white`; `Panel::favicon()` inlines the mark in the brand colour unless `vanda.favicon` is set; the sign-in page shows Vanda's liquid glass picture (`packages/renderer/src/assets/auth-background.webp`, built with a hashed name) under a frosted card; `vanda.auth_background` sets another URL or `false` for none. After signing in only the path of the intended URL is used.
- **Activity log** (`Vanda\Activity`, table `vanda_activity`): a model with `RecordsActivity` records who created, changed, deleted or restored it, with the screen, the button and the values before and after (`ActivityOptions`: type name, title, `->screen()` link, `except()`, `secret()`, `labels()`; attribute names come from the screen's field labels, enum values are kept by their labels). Only changes made by buttons of Vanda screens are recorded unless `->everywhere()`. A button that changed no recorded model is recorded by itself (`#[Action(activity: false)]` turns that off; modal loads never count); sign-in, sign-out and impersonation too. `ActivityLog::note()` adds a line of your own. Screens: `ActivityListScreen`/`ActivityScreen` behind `platform.activity`; a record's history is `Layout::activity($record)` (Vanda's own `Role` records its changes too). Passwords, tokens and `$hidden` attributes are stored without values. `vanda.activity.enabled` turns it off, `keep_days` with `model:prune` removes old entries.
- **Notifications** for the bell are Laravel database notifications; send `Vanda\Notifications\PanelMessage` (Orchid's DashboardMessage data shape).
- **Assets** are hashed files listed in `resources/dist/.vite/manifest.json`; `Panel::entry()` reads it. Never load the entry with a query string: chunks import it by its plain URL, and a second URL means a second copy of React.
- **A new node type** needs three things in one change: the PHP class (extends `Vanda\Schema\Node`), a renderer component registered in `packages/renderer/src/nodes/NodeView.tsx`, and a test that checks its IR.
- **Expressions** (`Expr`) are evaluated in PHP and TS. Change both evaluators and add a case to `packages/schema/fixtures/expressions.json`; both test suites read it.
- **Errors explain the fix.** Throw `VandaException` with a message that says what is wrong, where, and what to write instead.
- **Pages are checked** (`Vanda\Schema\SchemaCheck`) in development, in tests, always in `vanda:inspect`, and for every routed screen at once by `vanda:check` (built for someone who may do everything, `Authorizer::$allowAll`, so parts hidden from some roles are checked too; a model parameter gets the first record of its table, a screen without one is skipped with the reason; anything a screen throws is reported with the `file:line` of application code): a field path, an `Expr` field or a `dependsOn` that the screen's declared state does not have (`StatePaths`: public properties of the screen and of its Forms; arrays, models and Repeater rows are not checked), a `ModalToggle` for a modal the screen has not, an icon the renderer does not draw. One exception lists every problem with the node, its `file:line` and «Did you mean …?» (`Support\Suggest`). Production pages are not checked. Anything new a node points at by name (a path, another node's id, a name from a fixed list) gets its check there in the same change. Icons: a new one goes into the map in `ui.tsx` and into `packages/core/resources/icons.json`; `icons.test.ts` keeps the two in step.
- **Tests first-class.** Screen behaviour is tested with `Panel::test(Screen::class, [...])->set(...)->call(...)` — no browser needed. `set()` takes only paths the user can edit on that screen (or a place inside one) and fails with «Did you mean …?» otherwise; `tamper()` sends what a forged request would, for tests that prove the server ignores it.
- PHP: `declare(strict_types=1)`, final classes unless meant for extension, docblocks on public API with a short example. TypeScript: strict mode, no `any` outside the node registry.
